# SmoothCraft 后续优化候选分析

> 基于 v1.0.4 的现状，逐个评估"还能往哪挖"。
> 所有"落点"都是在 Minecraft 26.1.2 的 jar 上 `javap` 核实过的，不是凭印象写的。

## 零、先谈测量：为什么下一步应该是它

现在所有优化都是按经验判断"哪里慢"。这很危险——你可能会花三天优化一个只占 5% 的环节，而真正吃掉 40% 的地方没动。

好消息是 26.1.2 的 `SectionRenderDispatcher` 提供了现成的可观测数据：

```java
public boolean isQueueEmpty();
public int getCompileQueueSize();
public String getStats();
```

配合已有的 HUD，加一行诊断几乎零成本：

```
区块 队列 128  实体 87  粒子 452
```

有了这个数字，"该优化谁"就不再是猜的。**建议先做这个，再做任何优化。**

---

## 一、第一档：低风险

### 1. 区块编译节流

**要治的问题**：跑图卡顿。注意这和"平均帧数低"是两件事——你站着不动 120 帧，一跑起来每 3 秒掉一次到 40 帧，这种"顿感"比全程 60 帧更难受。

**成因**：区块网格的编译结果要在主线程上传到 GPU。跑图时每帧都有新区块进入视野，编译任务集中完成，上传就挤在同一帧里，帧时间从 8ms 飙到 40ms。

**落点**：
- `SectionRenderDispatcher#schedule(CompileTask)` —— 派发编译任务
- `SectionRenderDispatcher#isQueueEmpty()` / `getCompileQueueSize()` —— 队列长度可读
- `LevelRenderer` 每帧会调用 `uploadGlobalGeomBuffersToGPU()`

具体做法：给每帧的"派发 + 上传"设一个数量上限，超出部分留到下一帧。队列积压时优先派发距离玩家最近的。

**预期收益**：不提高平均帧数，但能把帧时间尖峰削平。对"跑图手感"提升明显，体感上像是换了台机器。

**风险**：低。唯一副作用是区块出现在视野里的速度略慢（从"一帧内全出现"变成"两三帧分批出现"），但配合已有的视距爬坡，观感反而更连贯。

**工作量**：小～中。需要先定位到确切的派发/上传调用点，然后加一个带预算的包装。

**判定**：**推荐**。这是目前剩下的最大一块体感收益。

---

### 2. 实体追踪范围收敛（服务端）

**要治的问题**：服务器带宽 + 客户端实体数。

**现状**：原版按实体类型下发追踪范围，`EntityType#clientTrackingRange()` 是个固定值（单位是区块），掉落物默认给得和生物差不多。

**落点**：
- `EntityType#clientTrackingRange()` —— 返回值可按类型钳制
- `EntityType#updateInterval()` —— 位置同步间隔，同样可调

**做法**：给 `minecraft:item` / `minecraft:experience_orb` 这类"数量多、个体不重要"的实体收紧追踪范围（比如从 10 个区块收到 4 个），并拉长位置同步间隔。

**预期收益**：服务端发包量下降，客户端实体表变小（连带我们的剔除逻辑也更省）。玩家密度高的服务器收益更明显。

**风险**：低～中。远处掉落物会"看不见"——但它们本来就在 32 格外被我们剔除了，所以视觉上几乎无感。真正的风险是**拾取判定**：客户端看不到 ≠ 服务端没有，拾取由服务端判定，所以不影响功能。

**工作量**：小。

**判定**：**推荐（多人场景）**。单人几乎没有收益（集成服务器不走网络栈的理论优势有限）。

---

### 3. 小物件剔除

**3a. 经验球同格聚合**

刷怪塔门口常有一片经验球。它们和掉落物一样是"个体数量多、视觉重叠"的典型。

- 落点：复用现有的 `ItemAggregator` 思路，在 `EntityRenderDispatcher#shouldRender` 里对 `ExperienceOrb` 做同格去重。
- 注意：经验球的"同格"粒度要比掉落物粗一些（它们会被吸向玩家，位置更集中），建议按 2×2×2 区块合并。
- 风险：低。经验球本来就在闪烁，少画几个几乎看不出来。

**3b. 告示牌文字距离剔除**

告示牌的文字是单独渲染的（`SignRenderer` 的文本部分），距离远了字也看不清。

- 落点：`SignRenderer` 的文本提交部分，按距离跳过。
- 风险：低。风险点在于"远处的牌子看起来是空白的"，但那么远本来也读不清。

**预期收益**：中小。属于"顺手做掉"的类型，不是主要矛盾。

**判定**：**可做，优先级低于 #1**。

## 二、第二档：收益大，但会改变体验

### 4. 同格实体碰撞剔除（服务端）

**要治的问题**：农场里成百个实体挤在一格里，每个都在和其它实体做碰撞与推挤计算，复杂度是 O(n²)。

**落点**：`Entity#push(Entity)` 是实体互推的统一入口（已确认存在）。可以在实体数量超过阈值时，让同格实体跳过互推。

**预期收益**：刷怪塔/农场场景服务端 MSPT 明显下降。

**风险**：**中**。物品被推开的散落模式会改变——原本会散成一圈，现在可能堆在原点。玩家能察觉到，但不会影响功能（拾取、消失都不变）。建议做成"仅当同格实体数 > N 时启用"，平时完全不干预。

**工作量**：中。需要统计同格实体数，且要注意不能影响玩家自己（玩家永远正常推挤）。

**判定**：**观察**。先看诊断数据里服务端 MSPT 是否真的被实体推挤占满，再决定。

---

### 5. 远处方块实体 tick 节流（服务端）

**要治的问题**：漏斗、熔炉、刷怪笼在远处仍然每 tick 跑逻辑。大型自动化农场里这些能占掉可观的 MSPT。

**落点**：`LevelChunk#tickBlockEntities` 或 `BlockEntityTicker` 的调用处。

**预期收益**：自动化基地场景明显。

**风险**：**中偏高**。产出速度会变慢——玩家第一反应是"我的农场坏了"，这是最难解释的一类改动。而且"隔刻 tick"对漏斗链的影响是累积的，可能造成物品卡在中间。

**判定**：**暂不做**。要做也必须默认关闭 + 明确提示。

---

### 6. 远处生物动画冻结

**结论：不可行/无收益。** 这条要专门说，因为它看起来很像一个"聪明点子"。

**原因**：我查了调用顺序——`LevelRenderer` 是先调 `EntityRenderDispatcher#shouldRender()`，通过了才会去 `extractRenderState()`。也就是说，**被我们的距离剔除掉的实体，本来就不会提取渲染状态、不会算动画**。

所以"冻结远处生物动画"要么是重复劳动（已经被剔除的不需要冻），要么必须对"未被剔除但很远"的实体下手——那部分距离区间很窄，收益微乎其微。

**判定**：**不做**。

---

## 三、第三档：不建议

### 7. AI 节流（降低寻路频率）

怪物行为会变呆：卡在拐角、不打人、怪物塔效率下降。这是"用玩法换性能"，在一个标榜"不改玩法"的模组里不合适。

### 8. 随机 tick 节流

作物、草方块、树叶的生长变慢。所有农场玩家都会反对。

### 9. 服务端真合并实体

把附近同类掉落物合并成一个实体。收益最大（tick + 渲染双省），但会改变：拾取判定、漏斗行为、消失计时、农场判定逻辑。这是"做另一个模组"的量级，不是优化开关。

---

## 四、结论与建议顺序

| 顺序 | 做什么 | 理由 |
| --- | --- | --- |
| 1 | **诊断行**（队列/实体/粒子计数） | 零风险，拿到数据才能定向优化 |
| 2 | **区块编译节流** | 剩下来最大的一块体感收益，风险低 |
| 3 | **实体追踪范围收敛** | 多人服务器性价比高，改动小 |
| 4 | 经验球聚合 + 告示牌文字剔除 | 顺手做，收益中等 |
| 5 | 同格碰撞剔除 | 等诊断数据证明必要再做 |
| — | 动画冻结 / AI 节流 / 真合并 | 不做（前者无收益，后两者动玩法） |

一个原则：**每一次优化都应该能在 HUD 上看到一个对应的数字变化**。看不到数字变化的优化，很难判断它到底有没有用，也很难在出问题时回滚。
